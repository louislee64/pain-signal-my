# Reporting, alerting and scheduling

Milestone 7. PROJECT_SPEC.md §37 (jobs), §38 (scheduling), §39 (weekly report),
§40 (alerting).

The acceptance criterion is that **report generation is automatic and
reproducible from stored data**. Both halves are load-bearing, and reproducible
is the one that constrains the design.

---

## Reproducible

Three rules, each of which rules out something that would otherwise be natural to
write:

**Nothing reads the clock.** Every query in `ReportBuilder` is bounded by the
window passed in. One `whereDate(..., '>=', now()->subDays(7))` anywhere would
quietly break reproducibility for the section that used it, and the breakage
would be invisible until someone regenerated an old report and got a different
answer.

**Nothing is generated by an LLM.** §41: *"Never allow AI-generated summaries to
replace raw evidence."* The executive summary is assembled from the same figures
the sections report, so it cannot contradict the body and it renders identically
every time.

**Every ordering is total.** Each sort has a tiebreak on `id`. Two opportunities
with the same score would otherwise come back in whatever order Postgres felt
like, and the content hash would flap between runs on identical data.

### The hash

`content_hash` is SHA-256 over the *structured sections plus inputs*, not the
Markdown. The renderer is pure, so identical sections always render identically;
hashing the prose instead would make a wording change look like a data change —
the opposite of the signal the hash exists to carry.

`generated_at` is excluded. It is metadata about the run, not about the findings,
and including it would make every report trivially unique — turning the
reproducibility check into a tautology.

`JSON_PRESERVE_ZERO_FRACTION` matters more than it looks: without it `45.0`
encodes as `45` while `45.5` encodes as `45.5`, so a score landing exactly on an
integer would hash differently from the same score computed a hair off.

```bash
docker compose exec api php artisan reports:generate --week-ending=2026-08-08 --verify
#   hash: d91f2f0eaaa3402defd7d513951e2ec7a459d1ccda52d3a03edc00de60f33b86
#   reproducible: yes — rebuilding produced an identical hash
```

A mismatch is **not necessarily a bug**. Recording an interview for a past week
legitimately changes that week's report. The check reports the facts and leaves
the judgement to a person; `GET /api/v1/reports/{id}/verify` and the button on
the report page do the same.

### The window

Exactly seven inclusive days: `subDays(6)`, not `subWeek()`. Consecutive weekly
reports then neither overlap by a day nor skip one.

Both the command and the endpoint default to **yesterday**, never today. A period
still in progress would produce a report that changes if regenerated an hour
later.

## §39's eight sections

| Section | What it answers | Notable decision |
|---|---|---|
| Executive Summary | Top 3 findings | ordered by how much a finding should change behaviour, not by score — a payment beats a mention count |
| Rising Problems | What accelerated | only topics with *more* mentions than the prior window; a steady topic did not accelerate |
| Commercial Opportunities | Top ranked | confidence sits beside every score (§30) |
| New Signals | Previously unseen | ranked on **first-seen**, not recent activity — otherwise it returns the busiest topics, which are by definition not new |
| Buyer Evidence | Interviews and commercial signals | money is split out from the other eight evidence types (§7 Gate 4) |
| Opportunities to Ignore | High attention, poor monetization | kept separate from "already marked IGNORE" — a human decision should not be re-litigated weekly |
| Suggested Experiments | What to validate | derived from the next unmet §7 gate; experiments already running are not re-suggested |
| Build Recommendation | What to build | **capped at 2** (§39: "Do not recommend building 10 products simultaneously") |

Growth from a zero baseline reports as `new this period` rather than as a
percentage. Growth from zero has no finite value, and a large number would let a
topic's first two mentions outrank a genuine surge.

The build cap reports what it excluded. Silently truncating would read as "these
are all there are" rather than "these are the two to start with".

A quiet week says so. `quiet_period: true` and a sentence explaining that nothing
of commercial significance happened — that is a finding, not a formatting
problem, and three padded bullets would imply otherwise.

### Personal data survives into the report

§21's posture has to hold in a document that gets emailed and posted to Discord —
the worst possible place for a leak. Interviews render their pseudonymous
`company_ref`, industry and role. **Notes are deliberately not rendered**: they
are free text an operator typed, and free text is where a name ends up. There is
a test for this.

## §40 alerting

The hard part is not detecting the conditions — most are a query. It is that
they are **standing facts, not events**. "Opportunity reaches SELL_PILOT" stays
true for as long as the recommendation holds, so a naive scheduled evaluation
re-fires it every night. A channel that repeats itself daily gets muted within a
week, and then the one alert that mattered goes unread.

Every rule therefore produces a `dedupe_key`, unique in the database. "Have we
already said this?" is answered by an insert failing rather than by a read that
could race a concurrent run.

| §40 condition | Dedupe key | Why that key |
|---|---|---|
| Score increases significantly | `score_increase:{id}:band{n}` | 10-point bands, so a slow climber alerts once per band rather than weekly |
| New topic enters Top 10 | `top10_entry:{id}` | rank excluded — shuffling #7 → #6 is not news |
| Major trend anomaly | `trend_anomaly:{keyword}:{date}` | same spike stays quiet; a fresh spike next week alerts |
| Multiple independent sources on a new issue | `corroborated_new_issue:{topic}:{first_seen}` | distinct **sources**, not documents (§31) |
| Commercial evidence added | `commercial_evidence:{id}` | one row, one alert |
| Reaches SELL_PILOT / PRODUCTIZE | `recommendation_milestone:{id}:{rec}` | includes the recommendation, so PRODUCTIZE is not suppressed by an earlier SELL_PILOT |

**Baselines.** The first run records a `:baseline` row per opportunity, marked
delivered so it never sends. Without it, an opportunity that has always been at
80 would alert as though it had just got there.

**Severity.** A payment is `critical`; stated interest is `info`. §7 Gate 4:
paying is "considerably more valuable than 'I would probably use this'".

**Detection is separate from delivery.** `alerts:check` detects; `--notify`
delivers. An alert detected but not delivered stays pending and goes out on the
next run, oldest first — if delivery has been broken for a while the backlog
should arrive in the order it happened, not tell the story backwards.

## Notification channels

Defaults to `log` alone. Nothing leaves the machine until an operator names a
channel — the same posture as LLM extraction, and for the same reason: a system
that posts commercial findings to Discord as a side effect of someone running a
command has surprised its operator.

```bash
docker compose exec api php artisan notifications:status
docker compose exec api php artisan notifications:status --send-test
```

| Channel | Needs | Notes |
|---|---|---|
| `log` | nothing | always works; makes "notifications are off" observable rather than silent |
| `discord` | `DISCORD_WEBHOOK_URL` | splits on blank lines at 1900 chars — Discord rejects >2000, and truncating would drop the Build Recommendation section |
| `email` | `REPORT_EMAIL_TO`, a real `MAIL_MAILER` | refuses when `MAIL_MAILER=log`, which "works" and delivers nothing |

Configured in `apps/api/config/notifications.php` from `.env`, not in the shared
`config/*.yaml` tree — a webhook URL is a credential and does not belong in a
file committed to git and mounted into two containers.

Failures are per-channel and never throw. A broken webhook must not stop the
email, and neither must stop the report being stored: the report is the
deliverable, the notification is a courtesy.

## §38 scheduling

```bash
docker compose exec api php artisan schedule:list
```

```
0  1 * * *   intelligence ingest data_gov_my_fuelprice   official data
30 1 * * *   intelligence normalize                      after ingestion
0  2 * * *   intelligence classify                       after normalization
30 2 * * *   intelligence trends compute                 daily
0  3 * * *   intelligence aggregate                      metrics, daily
30 3 * * *   intelligence score                          scoring, daily
0  4 * * *   alerts:check --notify                       after scoring
0  6 * * 1   reports:generate --notify --verify          weekly
```

Every entry is `withoutOverlapping()`. A large ingestion can outlast its own
interval, and two concurrent runs of one collector would both insert, both hit
the content-hash dedup in different orders, and produce an `ingestion_runs`
history nobody can read.

**LLM extraction is deliberately not scheduled.** It is the one stage that spends
money per document, and a nightly job that quietly bills an API is exactly what
`config/llm.yaml`'s `enabled: false` default exists to prevent.

**Nothing runs it by default.** The compose stack starts no scheduler. Add one
deliberately:

```bash
docker compose exec api php artisan schedule:work     # foreground, for trying it
# or a host cron:
* * * * * cd /path/to/repo && docker compose exec -T api php artisan schedule:run
```

The Python stages shell out to the intelligence CLI rather than being
reimplemented as Laravel jobs. §37 lists both kinds of worker, and the split stays
where it already is: Laravel owns the schema and the API, Python owns collection
and scoring. Override the invocation with `INTELLIGENCE_CLI` if your scheduler
cannot reach `docker compose`.

## §38 conditional fetching

> "Do not download unchanged official datasets unnecessarily. Store:
> `last_modified`, `etag`, `dataset_version`, `last_successful_sync` where
> available."

This lands here because Milestone 7 is what makes ingestion automatic. Fetching a
dataset by hand occasionally is harmless; re-downloading it nightly when the
upstream file has not changed wastes a public service's bandwidth that we use
under its terms (§11).

The collector interface gained `collect(since, fetch_state)` and
`fetch_state()`. A collector that can make a conditional request sends
`If-None-Match` / `If-Modified-Since` and raises `SourceUnchanged` on a 304.

`SourceUnchanged` is an exception rather than an empty iterator because the two
mean different things: "the dataset is unchanged" is a successful outcome, while
"the dataset is now empty" is a problem. Collapsing them would let a source that
started returning nothing look like a source that simply had no news.

**`last_successful_sync` vs `last_synced_at`.** The first records that we
received data; the second that we talked to the source at all, including a 304 or
a failure. A source answering 304 for a month must not look like one delivering
fresh data daily — and `since` resumes from `last_successful_sync`, because
resuming from "when we last tried" would skip anything published between a failed
run and the next one.

**What actually happens with data.gov.my:** it sends neither `ETag` nor
`Last-Modified`, so the conditional path never engages for the one source wired
up so far. The saving there comes from the existing server-side `date_start`
filter instead — a second run returns 0 rows rather than 945. The plumbing is
built, tested against a mock transport, and ready for the next source that does
expose validators. Saying so beats implying a saving that is not happening.

## Endpoints

```
GET  /api/v1/reports                  history (no body — a year of prose is a lot)
GET  /api/v1/reports/{id}             one report, markdown served as stored
POST /api/v1/reports/generate         §36; `notify` is opt-in per request
GET  /api/v1/reports/{id}/verify      rebuild and compare
GET  /api/v1/alerts                   §40 history, `?pending=1` for undelivered
```

The list omits `markdown` and `sections`: a year of weekly reports is a large
amount of prose, and returning every word makes the history page slow at exactly
the point it becomes useful.

`show` serves the stored Markdown, never re-rendered. A report that changed under
the reader would be useless as a record of what was known when a decision was
made.

`POST /reports/generate` does not notify unless asked. Someone regenerating a
report to look at it should not thereby post it to a team channel — the scheduled
run is what notifies.
